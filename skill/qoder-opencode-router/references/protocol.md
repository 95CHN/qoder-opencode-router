# 协议与设计论证

## 1. 形态选型：为什么是 Skill 而不是 Plugin

| 判据 | 本任务实际情况 | 结论 |
|---|---|---|
| 能力数量 | 只有「派单—执行—验收」一条闭环 | 单一能力 → Skill |
| 是否角色工具箱 | 不是某职业的多任务套件 | 不需要 Plugin 的多 skill 结构 |
| 外部依赖类型 | 本地 CLI 可执行文件，不是 MCP 服务 | `.mcp.json` / `CONNECTORS.md` 无用武之地 |
| 是否需要 hooks/agents | 不需要；环境自检放在脚本 `doctor` 里按需跑 | Plugin 的附加组件全是负担 |
| 分发方式 | 本地 ZIP 经 `install_extension` 安装，Skill 与 Plugin 同样支持 | 分发不构成选 Plugin 的理由 |

Plugin 的价值在于「一个角色的一整套能力 + 连接器编排」。本任务是一个能力，套 Plugin 外壳只会多出 `plugin.json`、目录层级与维护面，且用户调用时多一层选择成本。**选 Skill**：`SKILL.md` + `scripts/router.py` + `references/`。将来若要扩成「外包套件」（如批量派单、成本统计、多工并发），再升级为 Plugin 并把本 Skill 作为其中一个能力。

## 2. 连接方案：分体 md 胜出，台账补齐可读性

### 2.1 两种方案的真实成本

设系统前缀 S、单任务契约 P、单份报告 R，均为 token 量级（实测 P≈1.5k、R≈0.6k、S≈5k）。

| 指标 | 分体（每任务独立目录） | 合体（共用两份 md 增量追加） |
|---|---|---|
| opencode 单次输入 | S + P（恒定） | S + Σ(P_i + R_i)（随历史线性增长） |
| n 个任务累计输入 | n·(S+P) | n·S + O(n²)·(P+R) |
| Qoder 侧读报告 | R（恒定小） | 全部历史报告（线性增长） |
| 串任务风险 | 目录隔离 + TASK_ID 校验，低 | 高：历史指令与新指令同屏，模型易执行旧步骤 |
| 返工定位 | 同会话续跑，只发增量 | 需在长文中定位段落，易改错位置 |
| 用户可读性 | 差（文件散落）→ **用 INDEX.md 台账补偿** | 好（单页可追溯） |

### 2.2 关于缓存命中率的一个常见误解

「合体增量追加会破坏缓存」并不准确：**追加在文件尾部时前缀不变，前缀缓存仍然命中**。实测证据（本机 opencode v2.3.0，deepseek-v4.1-flash-free）：

- 冒烟单步：`input=6437, cache.read=512`
- 两步任务第二步：`input=152, cache.read=6912` ← 前缀几乎全部命中

所以合体方案真正的代价不是缓存失效，而是：

1. **命中也要付钱**：cache read 仍是输入 token，历史越长每轮越贵，累计 O(n²)。
2. **上下文污染**：旧任务的步骤、旧交付路径、旧验收标准与新任务混在同一份文件里，免费模型（上下文与指令遵循能力有限）极易串执行。一次串任务的返工成本远高于省下的文件管理成本。
3. **Qoder 侧被动扩容**：读一份含全部历史的 report.md，等于把外包省下的词元又吐回去。

分体方案让每个任务的输入恒定，且 plan.md 一经派单即不可变 → 前缀稳定、缓存命中可预期。

### 2.3 最终协议：分体执行 + 单页台账

```
opencode-tasks/
├── INDEX.md                     # 脚本维护，给人看；Qoder 默认不读
└── T20261119-151200-hello/      # 目录名 = TASK_ID
    ├── meta.json                # 机器状态：ID/时间/模型/session_id/轮次/token
    ├── plan.md                  # Qoder 写，派单后不可变（ROUTER 头部由脚本校验）
    ├── report-template.md       # 随任务下发，保证 opencode 侧自包含
    ├── report.md                # opencode 写，Qoder 唯一读取的交工摘要
    ├── revision-01.md           # 返工增量（可选）
    ├── run-dispatch.jsonl       # 原始事件流，落盘不进 Qoder 上下文
    └── run-dispatch.err         # 失败时只 tail 末 20 行
```

用户要溯源时只看 `INDEX.md` 一页；要细节再点进对应任务目录。可读性由台账解决，不必牺牲执行隔离。

## 3. 进度对齐机制

四重对齐，任一不符即判 FAIL：

1. **TASK_ID**：`T<YYYYMMDD>-<HHMMSS>-<slug>`，目录名 = plan 头部 = report 头部。`verify` 做字符串比对，串号直接失败。
2. **时间戳**：plan 的 `CREATED_AT`、report 的 `REPORTED_AT`、meta 的每轮 `at`，均带时区，可判断先后与是否旧报告冒充新交付。
3. **编号追溯**：plan 的 G/S/A 编号 ↔ report 的逐条自检 A1..An ↔ revision 的问题编号。验收不靠感觉，靠编号对账。
4. **ROUND**：首次交付为 1，返工递增；report 的返工记录追加不覆盖，保留审计链。

## 4. 返工为什么用同会话

`revise` 通过 `--session <session_id>` 续跑原会话：系统前缀与 plan 内容已在缓存中，只需发送增量问题清单。相比「新开任务重发全量背景」，输入 token 降一个量级，且模型记得自己刚做过什么，改动更精准。session_id 由脚本从事件流里提取并存进 meta.json，Qoder 不需要知道它。

## 5. 质量保障（省钱不能降质）

- 默认推理档位 **high**，只有用户明确要求才降档。
- 验收标准必须可判定，报告必须给真实执行输出，禁止编造。
- 两段验收：脚本做结构校验（ID/存在性/非空/可选 CHECK 命令），Qoder 做语义验收（逐条对 A 编号）。
- 最多 2 轮返工后上报用户，避免无限重试。

## 6. 已知失败模式与对策

| 失败模式 | 对策 |
|---|---|
| CLI 不在 PATH（桌面版自带） | `doctor` 多路径探测，含 `ai.opencode.desktop*/resources/opencode-cli.exe` |
| 权限询问导致挂起 | 固定 `--auto`，并在 plan 中限定可改动文件范围 |
| 报告缺失/敷衍 | `verify` 判长度与 TASK_ID；缺失即返工 |
| 模型名/变体写错 | `resolve_model` 模糊匹配 + 变体白名单，匹配不到就列候选让用户选 |
| 网络/代理 | `--proxy` 显式注入子进程环境变量（CLI 不读系统代理） |
| 长任务超时 | `--timeout` 可调，默认 900s；超时 kill 并留日志 |
| 中文输出乱码 | 子进程统一 UTF-8 + errors=replace；plan 要求文件 UTF-8 |
